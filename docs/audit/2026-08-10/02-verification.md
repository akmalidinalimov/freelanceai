### /api/me/portfolio is the one attachment surface with no isOwnUpload gate — stored external URL + server-side fetch

**DOWNGRADED → MEDIUM** · reachable today: **yes**

**Proof.** src/server/services/portfolio-l0.ts:79 — `const res = await fetch(item.mediaUrl, { signal: ctrl.signal }).finally(() => clearTimeout(timer));` reached from src/app/api/me/portfolio/route.ts:23 (`void measureItem({ id: item.id, mediaUrl: item.mediaUrl, ... })`) with `mediaUrl: z.string().url().max(500)` (route.ts:10) and no isOwnUpload call. Grep confirms isOwnUpload exists in exactly 5 routes (conversations messages:47, me/avatar:13, onboarding:32, orders:31, orders/[id]:40) and not this one. Self-serve reachability confirmed: onboarding/route.ts:44-47 sets `isSeller: true` with no approval, and authz.ts:44-49 `requireSeller` only checks `user.isSeller`.

**What the original missed.** Severity inflation on the SSRF half. (1) The SSRF is fully BLIND with no oracle on the attacker's own surface. measureItem is fire-and-forget (`void ... .catch(() => {})`), so the POST returns before the fetch resolves — no timing signal, no body. (2) The claim that 'reachable vs unreachable is recorded in the item's issues' is FALSE for this path: `issues` is only on the returned in-memory object, which route.ts:23 discards. The only DB write (portfolio-l0.ts:110-121) persists width/height/bytes/phash/analyzedAt — never `issues` — and it sits AFTER `sharp(buf).metadata()` (line 92), so any non-image response throws into the catch at line 122 and the update never runs. A port-scan therefore writes nothing observable. `issues` escapes only through runL0, whose only two callers are src/app/api/admin/portfolio-review/route.ts:7 (admin-only) and src/server/services/gig-review-packet.ts:81 (admin Telegram packet) — the attacker cannot read either. (3) No cloud metadata service exists to hit: deploy/docker-compose.prod.yml is a Hostinger VPS docker-compose behind a Cloudflare tunnel; the `169.254.169.254` PoC in the failure scenario returns nothing. The only in-network HTTP target is `app:3000` (the app itself, unauthenticated GET, no cookie) — `db` is Postgres, not HTTP. (4) The one surviving oracle is that width/bytes/phash appear on the item (readable via getOwnProfile) only if the internal endpoint returns a sharp-decodable image. What the original got exactly right and is the real value here: the stored-external-URL half is unmitigated — portfolio-showcase.tsx:53-55 renders a raw `<img src>` (so next.config.ts remotePatterns does not apply, that only guards /_next/image) and the ENFORCED CSP (next.config.ts:34-49) has no img-src; img-src is only in the Report-Only policy at line 61. Public visitor IP/UA harvesting and post-moderation content swap on /creators/<username> are real.

**Fix assessment.** The proposed one-liner is correct and is the right primitive (isOwnUpload already handles both public URLs and `r2-private:` refs via OWN_KEY_SHAPE, media.ts:188-201). Two caveats the fix text gets right and one it misses: (a) re-checking inside addPortfolioItem is indeed needed because onboarding also calls it — but onboarding already gates at route.ts:32, so this is belt-and-braces; (b) the instagram-sync path writes PortfolioItem rows with re-hosted R2 URLs, so a defensive check inside addPortfolioItem will not break it — but verify instagram-sync.ts does not call addPortfolioItem with a raw cdninstagram URL before landing the service-layer check, or IG sync will start throwing. Tightening measureItem to our own objects is the correct second layer and closes the SSRF independent of the route fix.

### Nightly production DB dump is unencrypted, in the same R2 bucket the app serves user files from

**DOWNGRADED → MEDIUM** · reachable today: **no**

**Proof.** deploy/docker-compose.prod.yml, backup service command: `if pg_dump -h db -U freelanceai -d freelanceai -Fc -f /tmp/$$F; then for K in $$F $$M; do curl -sf --aws-sigv4 aws:amz:auto:s3 --netrc-file /root/.nrc -T /tmp/$$F "$$EP/$$S3_PRIVATE_BUCKET/backups/$$K"` — the dump goes from pg_dump to curl with no gpg/age stage anywhere in the pipeline. docs/OPS-RUNBOOK.md:56 prescribes `pg_dump -Fc "$DB" | gpg --encrypt --recipient backup@yourdomain | aws s3 cp -` and docs/DATA-PROTECTION.md:25 states '**Backups:** encrypted (GPG public-key)'. deploy/restore-drill-compose.yml confirms no key is involved: it curls the object and runs `pg_restore -h db -U drill -d drill --no-owner --no-privileges /tmp/restore.dump` directly.

**What the original missed.** The exploit chain is credential-compromise-only — there is no path from any app user to the dump, which the finding implies but never states. I checked the one route that would make it remotely exploitable and it is closed: both download proxies validate the client-supplied key against stored membership BEFORE touching R2 — src/app/api/conversations/[id]/file/route.ts:22 (`if (!(await conversationHasFile(id, url))) throw Errors.forbidden(...)`) and src/app/api/orders/[id]/file/route.ts:22-25 (`order.deliveries.some((d) => d.fileUrls.includes(url)) || order.requirementFileUrls.includes(url)`), each only then calling resolveStoredFile+getObject. So `r2-private:backups/db-Mon.dump` cannot be smuggled through the app's credential. Two other blast-radius claims are weaker than stated: .env.deploy.local is untracked and matched by .gitignore:31 (`.env*.local`), so it is not in the repo; and the GitHub Actions exposure is opt-in — uptime.yml:33-35 explicitly no-ops ('backup-freshness check skipped (S3 secrets not configured)') when the S3 secrets are absent. Minor correction to the title: the buckets are distinct (S3_BUCKET=freelanceai-media, S3_PRIVATE_BUCKET=freelanceai-private), so this is not the public asset bucket — but the title is still accurate in substance, because freelanceai-private is where deliveries/requirements/messages live (media.ts:63, PRIVATE_PREFIXES) and it is the bucket the backup writes to, on the same S3_ACCESS_KEY_ID the app container receives. Also worth noting the fail-closed design the finding does not credit: the sidecar exits 1 ('FATAL: S3 not configured — refusing to run without offsite backups') rather than silently skipping, and S3_PRIVATE_BUCKET is in fact populated in .env.deploy.local, so the backups do exist and the finding's premise holds.

**Fix assessment.** Directionally correct but incomplete as written — applying only what it says will break two other things. (1) The sidecar is `postgres:16-alpine`, which has no gpg; the command must add `apk add --no-cache gnupg` alongside the existing curl install, and the public keyring has to be mounted or baked in. (2) Renaming the object to `.dump.gpg` silently breaks BOTH the freshness alarm (.github/workflows/uptime.yml, which HEADs `$EP/$BUCKET/backups/db-$D.dump`) and the restore drill (deploy/restore-drill-compose.yml, which GETs the same key and pipes straight into pg_restore) — the alarm would start firing 'no backup' on an encrypted-but-healthy backup, which is exactly the failure mode the alarm exists to catch. All three must change in one commit, and the drill must gain a `gpg --decrypt` stage with a key the drill box holds. (3) The 'separate bucket + separate credential' half is the more valuable part and should be sequenced first, since it removes the app container from the blast radius without touching the restore path.

### Blocked conversation is a silent, untranslated dead end — the designed notice string is never rendered

**DOWNGRADED → MEDIUM** · reachable today: **yes**

**Proof.** src/components/message-thread.tsx:382 — `<Button onClick={send} disabled={busy || (!input.trim() && files.length === 0)}>` — the `blocked` state (line 52) is consulted nowhere except the header label at line 222 (`{blocked ? t("unblock") : t("block")}`), despite the comment at line 51 claiming 'UI reflects + disables'. `grep -rn blockedNotice` returns messages/en.json:719, ru.json:719, uz.json:719 and zero hits in src/. The directional/bidirectional mismatch is also real: blocks.ts:9-19 counts `OR: [{blockerId: aId, blockedId: bId}, {blockerId: bId, blockedId: aId}]` while moderation-user.ts:34-42 looks up only `{ blockerId: user.id, blockedId: otherId }`.

**What the original missed.** Severity is inflated from a P2 polish bug to CRITICAL on two factual errors in the failure scenario. (1) 'Silent' is false — send() sets `setSendError(j.error?.message ?? t("sendFailed"))` at line 169 and it renders in a `role="alert"` paragraph at lines 387-389, so the user gets an explicit, screen-reader-announced error. The accurate complaint is 'untranslated and after-the-fact', not 'silent'. (2) 'She retries, re-types' is false — `setInput("")` and `setFiles([])` run only inside the `if (j.ok)` branch (lines 165-168), so the 200-word brief and every attachment survive the failed send. There is no data loss. Net impact: no security exposure, no money path, no lost work; a rarely-hit T&S feature on a pre-launch platform (~117 orders) producing one English error string instead of a pre-emptive localized notice. What genuinely holds it at MEDIUM rather than LOW is the theyBlocked case the original correctly identified: because hasBlockedCounterpart is directional while the server check is bidirectional, the blocked-by-counterpart user sees a 'Block' button, gets a forbidden error, and has no unblock control and no support surface — that is a real unrecoverable state, plus a genuine ENGINEERING-STANDARDS §8 violation in two files.

**Fix assessment.** Parts (1) and (2) are correct. Part (3) is WRONG as written and would make the UX worse: `Errors.forbidden("Message.conversationBlocked")` puts the literal key in `ApiError.message` (src/lib/api.ts:52), the envelope ships it as `error.message` (api.ts:32), and the client renders it verbatim via `setSendError(j.error?.message ?? t("sendFailed"))` (message-thread.tsx:169) — the user would see the raw string 'Message.conversationBlocked' on screen. There is no key-to-catalog mapping on the client and no `messageKey` field in the ApiResult error shape, so §8 compliance here requires either adding a machine-readable discriminator to the error envelope or having the client match on `error.code === "FORBIDDEN"` for this route. The fix also misses two sites: src/server/services/offer.ts:37 throws the identical hardcoded `Errors.forbidden("This conversation is blocked")` for custom offers, and src/app/[locale]/orders/[id]/page.tsx:201 renders `<MessageThread>` with NO `initiallyBlocked` prop at all (it defaults to false at message-thread.tsx:33), so the new notice would never appear on the order-page thread even for the blocker.

### Seller self-approves any gig past moderation via action:"resume"

**CONFIRMED → HIGH** · reachable today: **yes**

**Proof.** src/server/services/gig.ts:298-299 — `export const resumeGig = (gigId: string, user: GigActor) => updateOwnedGig(gigId, user, { status: "ACTIVE" }, "gig.resume");` — and the shared writer it calls, gig.ts:288-291, is `prisma.gig.updateMany({ where: { ...gigEditWhereForUser(gigId, user), deletedAt: null }, data })`, which for a non-admin expands (authz.ts:66-69) to `{ id: gigId, sellerId: user.id, deletedAt: null }`. Ownership only. There is no `status` predicate anywhere on the path, so PENDING_REVIEW/REJECTED/DRAFT → ACTIVE is a legal owner-driven transition. Contrast gig.ts:415-416 (`publishGig`) which does carry `status: "DRAFT"` in its where-clause, and gig.ts:335 (`moderateGig`) which throws FORBIDDEN for non-admins — proving the status precondition is a deliberate pattern that `resumeGig` simply omits. I re-read the route (src/app/api/gigs/[id]/route.ts:82-99) looking for a guard the original agent missed: there is none — only `isSameOrigin` + `getCurrentUser`, no `requireSeller`, no rate limit, and `action:"resume"` is in the zod enum at line 20-31.

**What the original missed.** Three things, two of which cut against the claimed blast radius and one that makes it worse. (a) Public visibility has a SECOND, independent gate the finding glosses: every public surface composes `PUBLIC_GIG_SELLER` (src/server/services/seller-visibility.ts:29-31 = `seller: { is: { isSeller: true, status: "ACTIVE", sellerProfile: { is: { approvalStatus: "APPROVED" } } } }`), and `approvalStatus: "APPROVED"` is written in exactly one place, `approveSeller` in admin-sellers.ts:85, behind `if (admin.role !== "ADMIN") throw Errors.forbidden` at line 70. So the attacker must already be a human-vetted seller — the exploit defeats PER-LISTING moderation, not the platform's first-contact moderation. (b) The finding notes `createOrder` (order.ts:34-35) only checks `status: "ACTIVE"` and omits PUBLIC_GIG_SELLER — true, but a buyer cannot reach an unapproved seller's gig page at all, because `getGigBySlug` (gig.ts:607-609) does compose PUBLIC_GIG_SELLER, so there is no discovery path to that gigId. (c) Worse than reported: the Resume button also fires on DRAFT (gig-row-actions.tsx:38-46 renders it for every status !== "ACTIVE"), so a DRAFT goes straight to ACTIVE, skipping PENDING_REVIEW entirely — sitting one pixel away from the correct `publish` button (line 33-37) that routes the same gig to PENDING_REVIEW. And the seller dashboard renders this for every gig regardless of status (dashboard/seller/page.tsx:361, fed by `listSellerGigs` whose where is only `{ sellerId, deletedAt: null }`, gig.ts:273). I could not find any middleware guard — src/middleware.ts:45 explicitly excludes `/api` from its matcher.

**Fix assessment.** Correct and sufficient in mechanism. `resumeGig` scoped to `status: "PAUSED"` closes it, and widening `publishGig` to `status: { in: ["DRAFT", "REJECTED"] }` gives resubmission a legitimate PENDING_REVIEW path — necessary, because without it a REJECTED gig has no forward transition at all and sellers are stuck. Two gaps in the proposed fix: (1) `updateOwnedGig` uses `updateMany` and throws `Errors.notFound` on `count === 0`, so a PAUSED-scoped resume on an ACTIVE gig will surface as a misleading 404, not the CONFLICT the fix text promises — the precondition has to be a separate read or the error mapped explicitly. (2) The fix only patches the UI for `gig-row-actions.tsx`; the API is the actual boundary, and both must change, since `POST /api/gigs/<id>` is directly callable with any same-origin fetch.

### An admin-approved gig can be rewritten wholesale without re-review — bait-and-switch past moderation

**DOWNGRADED → MEDIUM** · reachable today: **yes**

**Proof.** src/server/services/gig.ts:213-253 — `await tx.gig.update({ where: { id: gigId }, data: { title, description, coverUrl, coverFocal, coverType, coverPosterUrl, coverW, coverH, galleryUrls, categoryId, tags, portfolioTelegram, portfolioInstagram, faq, requirementPrompts, packages: { create: ... }, extras: { create: ... } } })` — the `data` object contains no `status` key, and lines 211-212 `deleteMany` the old packages/extras first, so it is a true wholesale replace on a live ACTIVE row. The docstring at gig.ts:194 states the intent outright: "Status is left unchanged." The claim that PATCH has no rate limit is also correct and I verified it: route.ts:106-118 is a hand-rolled handler (not `defineHandler`) with no `enforceRateLimit`, and src/middleware.ts:45 excludes `/api` from the matcher, so nothing throttles it.

**What the original missed.** Mainly that this finding is not independent of finding #1 — it is the same root cause and the same actor, and it grants that actor no capability they do not already have. Finding #1 lets a seller set ANY gig to ACTIVE at will with zero review, which strictly dominates 'edit an already-approved gig'. Rated on its own marginal risk, this is MEDIUM, not HIGH. Additional deflation: the failure scenario's '100,000,000 UZS package' is exactly the zod ceiling at route.ts:41 (`priceUzs: z.number().int().min(1000).max(100_000_000)`), i.e. the schema's intended maximum rather than an unbounded value; the edited gig stays publicly listed and `reportGig` (gig.ts:376) exists, so it is discoverable rather than covert; and with FREE_ORDERS=1 / PAYMENT_PROVIDER empty, a rewritten price cannot extract real money today. Confirmed accurate in the finding: `trendingScore` is a real persisted field (prisma/schema.prisma:456) and survives the edit, `listPendingGigs` (gig.ts:306-308) filters `status: "PENDING_REVIEW"` so an edited ACTIVE gig genuinely never resurfaces in the admin queue, and no notification fires on update (only `audit()` at gig.ts:255).

**Fix assessment.** Directionally right, but incomplete as written, and it must not ship alone. (1) It is worthless without also fixing `resumeGig`: demoting an edited gig to PENDING_REVIEW is undone by one click of the Resume button that finding #1 documents — the seller simply re-flips it to ACTIVE. The two fixes are a single change or neither works. (2) `updateGig`'s ownership check is `gigEditWhereForUser` (gig.ts:198), which returns `{ id: gigId }` for admins (authz.ts:67) — a naive `if (status === ACTIVE && changed) status = PENDING_REVIEW` would kick an ADMIN's own corrective edit back into the moderation queue. The demote must be gated on `user.role !== "ADMIN"`. (3) The 'moderated field changed' diff must include `galleryUrls`/`coverUrl`, which the fix mentions — this is the genuinely important part, because `stripContactInfo` (called at gig.ts:203-208 on title/description/FAQ and 246 on extras) still sanitizes all edited TEXT, so text abuse is partly mitigated on the edit path; image swaps are not sanitized at all.

### Telegram webhook rate limit is keyed on Telegram's own IP — one abuser silently blackholes the bot for every user

**DOWNGRADED → MEDIUM** · reachable today: **yes**

**Proof.** src/app/api/telegram/webhook/route.ts:35-37 — `if (!rateLimit(`tg-webhook:${clientIp(request)}`, 120, 60_000)) { return NextResponse.json({ ok: true }); // drop quietly under flood }` — combined with src/lib/rate-limit.ts:92-98, where in production `clientIp` returns `cf-connecting-ip` (which, for a webhook, is Telegram's delivery server) and otherwise the literal string `"unknown"`. Neither value is ever per-end-user, so this is one shared bucket for the whole bot. The two per-user limiters (`tg-cb:${cbFrom}` at :80, `tg-reply:${from.id}` at :174) are both downstream of line 35 and are unreachable once it trips. The team's own comment at route.ts:172-173 concedes the premise: "the global webhook limiter keys on Telegram's IP, not the end user". The backend is a single in-memory map (rate-limit.ts:30-53) in a single app container (deploy/docker-compose.prod.yml has one `app` service), so there is no per-instance dilution.

**What the original missed.** The mechanism is right; the HIGH rating overstates the consequence. (a) Availability-only, on a SECONDARY channel, and self-healing: it is a 60s fixed window (rate-limit.ts:42-44), so service resumes the moment the flood stops — no persistent state is corrupted. (b) Every affected capability has a working non-Telegram path: login has Google and email providers alongside the Telegram bridge (src/auth.ts:26-33 and src/app/[locale]/login/page.tsx:6-8), and the Mini App initData login (`verifyMiniAppInitData`, auth.ts:8) never touches the webhook at all; order accept/revise, chat replies, reviews and admin gig moderation all have web/admin-panel equivalents — the Telegram buttons are convenience wrappers over the same services. `startBotOnboarding` (bot-onboarding.ts:60) is just a Mini App deep-link button, not a stateful in-chat flow. (c) The '121 messages/minute' figure is optimistic for the attacker: Telegram delivers webhooks from 149.154.160.0/20 and 91.108.4.0/22 and Cloudflare passes the real source through `cf-connecting-ip`, so the bucket may split across several source IPs, making the practical threshold some multiple of 120/min. (d) One point the finding got right and understated: the drop is not even logged — there is no `console.warn` on the exceed branch, so the outage is invisible in ops, which is arguably the worst property of the code as written.

**Fix assessment.** Correct on both counts, with one ordering caveat. Keying on `message.from.id` / `callback_query.from.id` requires parsing the JSON body BEFORE the limiter — that is safe here because the secret-header check at route.ts:31-34 already returns 403 ahead of it, so only genuine Telegram traffic ever reaches the parse. Returning non-2xx on the global backstop is also safe as written, because the limiter currently sits BEFORE the `ProcessedUpdate` insert at route.ts:67-73 — no idempotency row is created for a dropped update, so a Telegram retry would actually re-process rather than being swallowed as a duplicate. That ordering must be preserved. The file already contains the correct pattern to copy: lines 186-194 delete the ProcessedUpdate row and return `{ ok: false }, { status: 500 }` precisely so Telegram redelivers.

### Both PSP webhooks return success to the provider even when no settlement happened — money collected, order dead

**DOWNGRADED → HIGH** · reachable today: **no**

**Proof.** src/server/services/payments.ts:131 `if (order.status !== "PENDING_PAYMENT") return; // already settled / closed — idempotent` (a void return), consumed unconditionally at src/lib/payments/payme.ts:133-138: `await settleOrderByProvider(txn.orderId, "PAYME", paymeId); await prisma.transaction.update({ where: { id: txn.id }, data: { status: "SUCCEEDED", ... } }); return { result: { perform_time: performTime, transaction: txn.id, state: 2 } };` — no branch on the outcome. Click mirrors it at src/lib/payments/click.ts:116-117: `await settleOrderByProvider(order.id, "CLICK", p.click_trans_id); return { ...base, merchant_confirm_id: ..., error: OK, ... }`. The `Already processed` guard really does exist only on Prepare (click.ts:104-107).

**What the original missed.** Three things. (a) Reachability: both webhooks are hard-inert in the current config. `verifyPaymeAuth` (payme.ts:48) requires `key === process.env.PAYME_KEY` with a non-empty key, and `verifyClickSign` (click.ts:66-67) returns false when CLICK_SECRET_KEY is unset — .env has PAYME_KEY="" and CLICK_SECRET_KEY="". No unauthenticated caller can reach the settle path at all, and no PSP is collecting money. CRITICAL implies live loss; this is a go-live gate, which the finding's own `ws` field already concedes. (b) The stated failure_scenario is not achievable as written: a 48h-expired order cannot be paid, because CheckPerformTransaction (payme.ts:63) and CreateTransaction (payme.ts:76) BOTH re-check `status !== "PENDING_PAYMENT"` and return ORDER_NOT_FOUND. The real window is only between CreateTransaction and PerformTransaction. (c) Conversely the original understated one thing: that window is user-controllable, not just a cron edge — `cancelOrder` (order.ts:396-408) lets the buyer cancel their own PENDING_PAYMENT order from the UI while a Payme txn is mid-flight, and `confirmOrderPayment` lets an admin manually settle into the same window. Partial recovery does exist (Payme CancelTransaction → payme.ts:140-161 → state -2 → Payme reverses the charge), so the buyer is not necessarily unrecoverable, but it requires them to complain to Payme.

**Fix assessment.** Correct and sufficient in shape. `postOrderPaymentTx` already returns boolean and `settleOrderByProvider` already computes `posted` (payments.ts:133) — plumbing it out is a 3-line change. Two additions the fix should make explicit: (1) the boolean must distinguish 'already settled by us' (idempotent retry — must still return state:2 / error:OK or Payme will loop forever) from 'order not settleable' (must return -31008); the current single `posted=false` conflates them, because `postOrderPaymentTx` returns false both when `idempotencyKey` already exists (payments.ts:38) and when the status claim misses (payments.ts:49). (2) On the Payme path the txn must also NOT be flipped to SUCCEEDED, otherwise a later CancelTransaction sees it as `paid` (payments.ts:183-186 looks for any SUCCEEDED PAYMENT_IN) and silently returns needsReview:false with no admin notify.

### No outbound refund path exists — refunds are posted to the ledger but never actually paid, and no admin surface lists them

**DOWNGRADED → MEDIUM** · reachable today: **no**

**Proof.** src/server/services/dispute.ts:83-92 writes `type: "REFUND", status: "SUCCEEDED"` with `provider: "MANUAL"` and no side effect other than `reversalPostings` (dispute.ts:93-101); the single settling line is dispute.ts:88 `status: "SUCCEEDED",`. Identical at cancellation.ts:71-80 and payments.ts:231-241. I read src/lib/payments/ in full — index.ts, payme.ts, click.ts — and the only exports are checkoutUrl builders plus inbound handlers; there is no receipts.cancel, no reversal, no outbound HTTP call of any kind. /admin/settlements (src/app/[locale]/admin/settlements/page.tsx:24-29) loads exactly listPendingPayments, listSellerBalances, listRecentPayouts, listPayoutRequests — no refunds section.

**What the original missed.** (a) Reachability: with FREE_ORDERS=1 and PAYMENT_PROVIDER empty, no buyer money is ever collected — every order is auto-settled by autoSettleFreeOrderIfEnabled (payments.ts:295-309) as provider MANUAL/isTest, so every REFUND row written today reverses a payment that never moved a som. The exposure is exactly zero across all ~117 orders. (b) 'no admin surface lists them' is overstated: refunds ARE surfaced in two places — the per-buyer Refunded total on /admin/users/[id] (admin-users.ts:248, rendered at admin/users/[id]/page.tsx:205) and the REFUND_HEAVY red flag (red-flags.ts:43,119). Neither is a who-is-owed-what work queue, so the operational point survives, but the absolute claim does not. **Proof.** src/server/services/review.ts:91 — `prisma.review.aggregate({ where: { gigId }, _avg: { rating: true }, _count: true }),` — the public gig-page rating aggregate, with no `order: { isTest: false }`, directly contradicting src/server/services/profile.ts:23 `prisma.review.aggregate({ where: { gig: { sellerId }, order: { isTest: false } }, ... })`. The write-side companion is src/server/services/review.ts:24 `if (order.status !== "COMPLETED") throw Errors.conflict(...)` — the last gate in createReview, and it never looks at order.isTest.

**What the original missed.** REACHABILITY BARRIER THE ORIGINAL GLOSSED OVER: this is approved-seller abuse, not an anonymous attack. Both the gig page and the order path require the attacker's own gig to be ACTIVE under an admin-APPROVED seller (getGigBySlug composes PUBLIC_GIG_SELLER, seller-visibility.ts:30; approvalStatus="APPROVED" is written in exactly one place, admin-sellers.ts:85, an admin-only action). A fresh account cannot self-serve into position — it must first clear the human seller-approval gate. Every already-onboarded Gigora seller does satisfy it.

BLAST RADIUS IS ONE PAGE, NOT THE SITE. getGigReviews is called from exactly one place (gigs/[slug]/page.tsx:71). Every other rating surface reads sellerProfile.ratingAvg/ratingCount, which recomputeSellerStats (profile.ts:22-23) filters on isTest: creator cards, /gigs and /categories cards, AI match scoring (match.ts:273-274 and 617-618), home, checkout-review.tsx, orders/[id]/page.tsx:82. Home testimonials filter it too (browse.ts:147). No money moves at all: test orders are excluded from seller balance (payments.ts:381, :398), tips are hard-refused (payments.ts:332 `if (order.isTest) throw ...`), and no referral credit is minted (order.ts:308).

THE ATTACK IS PARTLY SELF-DEFEATING. completeOrder calls recomputeSellerStats on every completion (order.ts:305), and that recompute overwrites the pre-launch demo numbers seeded by prisma/seed-demo-stats.mjs (24-139 reviews at 4.6-5.0, written straight onto SellerProfile for any profile with ratingCount=0). So each farmed order zeroes the attacker's own gig-card and creator-card stars while raising the detail-page headline. The finding's "the seller's own profile card shows the honest (filtered) number" is wrong twice over: that number is either 0 or a platform-fabricated 4.9 — never honest.

THE DEFAMATION VARIANT DOES NOT EXIST AT THIS RATE. A buyer cannot reach COMPLETED alone. deliverOrder (order.ts:258-261) is seller-or-admin only, and ORDER_TRANSITIONS (order-state.ts) only allows COMPLETED from DELIVERED or DISPUTED. 1-star-bombing a rival requires the rival to actually deliver each order, so it is not a 480/hr attack — only self-inflation is.

MISSED IN THE HARSHER DIRECTION (two things): (a) gig.ts:550 + gig-card.tsx:37 mean the fabricated ORDERS alone — one POST, no delivery/accept/review — inflate the visible "N orders" badge and the popular-sort rank across the whole marketplace, which is a strictly cheaper and broader abuse than the review loop the finding describes. (b) The post-go-live shape is inverted from what's implied: once FREE_ORDERS is removed, real orders carry isTest=false, so the missing check in createReview stops mattering for new orders and the exploit costs real money. The permanent residue is getGigReviews, which will keep folding today's pre-launch test reviews into the public star rating and the schema.org aggregateRating forever, in permanent disagreement with the sellerProfile number rendered 250 lines lower on the same page (gigs/[slug]/page.tsx:431-433).

SEVERITY: not CRITICAL. No money loss, no data exposure, no authz break. It is a trust-integrity defect on one page of a pre-launch site with near-zero organic traffic, entered through the admin approval gate. The two things that keep it at HIGH rather than MEDIUM are the crawlable self-serving aggregateRating (structured-data spam is a Google manual-action risk against Gigora's own domain) and the fact that it survives go-live untouched.

**Fix assessment.** HALF CORRECT, and the half that is wrong would break the platform today.

CORRECT: adding `order: { isTest: false }` to all three getGigReviews queries (review.ts:85, 91, 92) is the right and sufficient display-side fix. It also retroactively removes the existing ~117 orders' worth of test reviews from the public rating and the JSON-LD, which is the durable part of the defect.

WRONG TODAY: "Reject order.isTest in createReview". Under the current config freeOrdersEnabled() is true (payments.ts:283-286), so createOrder stamps isTest=true on EVERY order (order.ts:113/178) — honest ones included. Rejecting isTest in createReview would make the review step permanently 409 for every real user, and the documented purpose of the mode is the opposite: payments.ts:274-276 says free mode exists "so the full order -> chat -> delivery -> review flow can be exercised end to end without any payment". The ReviewForm at orders/[id]/page.tsx:214 would still render and always fail. Correct sequencing: land the getGigReviews filter now; gate createReview on isTest only when FREE_ORDERS is removed (or make the rejection conditional on !freeOrdersEnabled()).

INCOMPLETE: the fix does not touch the cheaper sibling abuse it shares a precondition with — gig.ts:550 sorts `popular` by `{ orders: { _count: "desc" } }` with no isTest and no status filter, and gig-card.tsx:37 renders `Math.max(gig.salesCount ?? 0, gig._count?.orders ?? 0)`. Step 1 alone (one HTTP call, no delivery, no accept, no review) inflates both. It also adds no per-buyer-per-gig order cap, which is the actual abuse lever; the only throttle in the whole chain is orders/route.ts:29.

The suggested long-term `Review.verifiedPurchase` flag is the right durable design.
