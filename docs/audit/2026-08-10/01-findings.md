## A — Login &amp; Session Integrity (P0)

### Telegram deep-link login is a one-tap account takeover (device-code phishing)

**CRITICAL → HIGH** (verified: DOWNGRADED, reachable today) · `src/app/api/telegram/webhook/route.ts:256` · confidence confirmed · effort M

**Claim.** The bot confirms a pending login token the instant it sees `/start <token>` — `loginToken.updateMany({ where: { token: payload, status: "PENDING" }, data: { status: "CONFIRMED", telegramId: String(from.id) } })` — with no consent prompt, no display of who requested the login, and no pairing code to compare. The `browserNonceHash` binding (src/app/api/auth/telegram/start/route.ts:35, checked at src/auth.ts:47) binds the session to the browser that *started* the login, which in this attack is the attacker's browser, so it provides zero protection. `isSameOrigin` on /api/auth/telegram/start (line 16) is a browser-CSRF check only — a `curl -H 'Origin: https://gigora.ai'` from the attacker's server mints a fresh token + nonce on demand, so the 5-minute TTL is not a barrier either. This is the primary, first, full-width login button on the page (src/app/[locale]/login/page.tsx:66) for a Telegram-native user base trained to tap bot links.

**Failure scenario.** Attacker runs a redirector. Victim taps a link (in a Telegram DM, a gig comment, an SMS: "confirm your Gigora payout"). The redirector server-side POSTs /api/auth/telegram/start with a spoofed Origin header, keeps token T and nonce cookie N, and 302s the victim to https://t.me/GigoraBot?start=T. The victim taps START in the *genuine* Gigora bot; the webhook flips T to CONFIRMED with the victim's telegramId. The attacker's poller (/api/auth/telegram/poll) sees `confirmed`, calls signIn("telegram", {token: T}) carrying nonce N, and auth.ts:47 passes because sha256(N) matches browserNonceHash. The attacker now holds a 7-day session as the victim — can read their inbox, request a payout to a new card, and accept deliveries. The victim's only signal is "✅ Tasdiqlandi! Saytga qayting" (webhook line 267), which reads like normal bot behaviour.

**Fix.** Make confirmation an explicit, informed act. In the webhook, do not CONFIRM on `/start <token>`: send an inline-keyboard message ("Kirishni tasdiqlaysizmi? Brauzer: <UA/city>, kod: AB-42") and only flip to CONFIRMED on the `Yes` callback_query. Store a short human-readable pairing code on LoginToken at /start creation, render it on the login page next to the button, and echo it in the bot message so the victim must match a code they never saw. Additionally require the callback's `from.id` to equal the `/start` sender, and shorten TTL to 2 minutes.

> **Verification (DOWNGRADED → HIGH).** Three corrections, one of which makes the attack EASIER than described. (1) The quoted where-clause is incomplete — the real code also requires `expiresAt: { gt: new Date() }`, so confirm-time expiry IS enforced; the attacker's window is a hard 5 minutes, not open-ended. (2) The whole isSameOrigin/curl-spoofed-Origin argument is unnecessary and slightly misleading: the attacker never needs to spoof anything. They open https://gigora.ai/uz/login in their own browser, click the real Telegram button (telegram-deeplink-login.tsx:27 fetches /start; the nonce cookie lands in their own jar), and forward the returned t.me deep link. isSameOrigin is irrelevant to this attack in both directions. (3) A scope limit the original did not state: src/lib/users.ts:66 upserts `where: { telegramId: tg.id }`, so the takeover only lands on accounts already keyed to that Telegram id. A Google/email-only victim with no telegramId is NOT taken over — tapping the link mints a brand-new user row instead. The victim population is Telegram-registered users only. Severity: this is UI:R (requires a victim tap inside a 5-minute window and an attacker-controlled delivery channel), which is CVSS ~8.8 High, not the zero-interaction/mass-exploitation profile that warrants CRITICAL. Blast radius today is a pre-launch user base, and no money leaves the platform even post-takeover (payouts are manually settled by an admin, and getSellerEarnings filters isTest:false so every balance is 0 under FREE_ORDERS=1). The session still yields full inbox/PII/order control, so HIGH stands and it must be fixed before launch.

### Impersonation overlay skips the target's status gate — suspended and deleted accounts become fully usable

**HIGH → LOW** (verified: DOWNGRADED, reachable today) · `src/lib/session.ts:30` · confidence confirmed · effort S

**Claim.** `getCurrentUser` enforces `user.status !== "ACTIVE" → null` on line 21 for the *session* user, but the impersonation overlay on lines 26-32 returns the target with only a `target.role !== "ADMIN"` check — no status check at all. /api/admin/impersonate/route.ts:32-34 likewise validates only `target.role`. So a SUSPENDED or DELETED (anonymized) row can be resurrected as a live principal. Downstream guards do not save it: `defineHandler` only checks `!user` (src/lib/handler.ts:47), and /api/me/payout/route.ts:13 checks `user.isSeller` but never `user.status` — `requireActive` (src/lib/authz.ts:39) is reachable only via `requireSeller`, which those routes don't call.

**Failure scenario.** A seller is suspended for fraud (admin-users.ts:405 sets status=SUSPENDED, and getCurrentUser normally locks them out on the next request). An admin — or anyone who has stolen an admin's session cookie — clicks "Log in as" on that suspended row. getCurrentUser now returns the suspended user for every request, so the platform's single suspension chokepoint is bypassed: they can post messages, place orders, and POST /api/me/payout to request a withdrawal of the fraudulent seller's balance, all while the account is nominally locked. The same works on a status=DELETED shell whose PII was already anonymized.

**Fix.** In src/lib/session.ts:30 require `target.status === "ACTIVE"` alongside `target.role !== "ADMIN"`, and reject the same in the POST at src/app/api/admin/impersonate/route.ts:34 so the admin gets an explicit error rather than a silently inert cookie. Separately, add `requireActive(user)` to the money routes (/api/me/payout) so status is enforced at the boundary and not only in the identity resolver.

> **Verification (DOWNGRADED → LOW).** Four mitigations that gut the severity. (1) The precondition is a genuine ADMIN session — impersonate/route.ts:24-28 resolves the raw `auth()` session and re-reads the DB row, the cookie is HMAC'd with AUTH_SECRET (impersonation.ts:23), and session.ts:26 applies the overlay only `if (user.role === "ADMIN")`. Admin comes solely from ADMIN_TELEGRAM_IDS, which holds exactly one id in prod (6542876935). This is not a cross-trust-boundary escalation. (2) The critical one: the same admin already has a one-click legitimate path to the identical outcome. admin-user-manage.tsx:204 renders "Reactivate" → setUserStatus(admin, id, false) → admin-users.ts:405 `data: { status: suspend ? "SUSPENDED" : "ACTIVE" }`, and loadTarget (admin-users.ts:391-398) imposes NO status precondition — so an admin can flip a SUSPENDED or even a DELETED row to ACTIVE, act, and flip it back. The overlay bypass grants zero capability the actor does not already hold. (3) It is not silent: impersonation start is audit-logged with actor + target (route.ts:45-51) and the UI renders an impersonation banner (src/app/[locale]/layout.tsx:79). (4) The specific money scenario in the failure_scenario is unreachable in the current config: requestPayout → getSellerEarnings (payments.ts:395-398) filters `isTest: false`, and FREE_ORDERS=1 stamps every order isTest, so availableUzs is 0 and payments.ts:551 throws "No withdrawable balance" before any row is written — and even on success it only creates a REQUESTED row an admin must manually settle. So: a genuine missing invariant, but admin-only, audited, no privilege gain, and no money path. HIGH is inflated by roughly two levels.

### Impersonation grants unrestricted write authority, and every resulting action is audit-logged as the victim

**HIGH** · `src/server/services/account.ts:114` · confidence confirmed · effort M

**Claim.** The overlay replaces the principal wholesale, so services receive the target `User` and stamp the target's id as the actor. `deleteOwnAccount` calls `anonymizeAndClose(user, user.id, "account.delete")` → `audit({ actorId, ... })` at account.ts:166, i.e. an admin-triggered irreversible anonymize-and-close is recorded as the victim deleting themselves. Same shape for escrow release: order.ts:327 `completeOrder(order, { actorId: buyer.id })`, and for /api/me/payout. `audit()` (src/lib/audit.ts:13-33) has no `impersonatedBy` / on-behalf-of field, and only `admin.impersonate.start`/`.stop` are logged — nothing in between. Compounding it, `signOut` (src/app/api/auth/logout/route.ts:10) never clears `gigora_imp` and auth.ts declares no `events.signOut`, so the `.stop` event can simply never fire and the overlay silently resumes when the admin signs back in within 30 minutes.

**Failure scenario.** An admin (or a phished admin session) impersonates a seller and POSTs /api/me/delete with {confirm:"DELETE"}. The account is irreversibly anonymized — telegramId, email, phone, portfolio and R2 objects gone (account.ts:169-241) — and the only DB record is `actorId = <victim>, action = "account.delete"`. During an incident review the trail exonerates the admin and blames the user. The same pattern lets an admin accept a delivery on the buyer's behalf, releasing escrow to a seller, with the ledger posting attributed to the buyer.

**Fix.** Two changes. (1) Thread the real actor through: have `getCurrentUser` return the overlay with an `impersonatedBy` marker (or expose a request-scoped `actingAdminId()`), and add an `onBehalfOfActorId` column to AuditLog that `audit()` populates automatically so no service can forget it. (2) Denylist irreversible/financial mutations while the overlay is active — /api/me/delete, /api/me/payout, order accept, payout-card change — by rejecting them in `defineHandler` when `impersonatedUserId()` is non-null; support impersonation should be read-mostly. Also add `events.signOut` to auth.ts to delete the impersonation cookie and emit the `.stop` audit row.

### /api/me/export returns decrypted PII with no audit entry, violating the stated standard

**MEDIUM** · `src/app/api/me/export/route.ts:10` · confidence confirmed · effort S

**Claim.** `exportOwnData` (src/server/services/account.ts:29) returns `account: { ...user, phone: decryptPII(user.phone) }` — the full user row with the Sensitive-tier phone decrypted, plus every order, review, payout and follow. `grep 'audit(' src/server/services/account.ts` returns exactly one hit (line 166, in anonymizeAndClose): the export path writes no audit row at all. docs/ENGINEERING-STANDARDS.md §12 states "Audit every money/PII/admin action", and src/lib/audit.ts:8 names "data export/erasure" explicitly as a call site. Combined with finding #2/#3, this is an admin-usable PII exfiltration channel that leaves no trace beyond a single `impersonate.start` row.

**Failure scenario.** An admin impersonates any user and issues GET /api/me/export. They receive that user's decrypted phone number, full order history and financial records. Nothing is logged. Repeated across the user base this is a bulk PII harvest, and after the fact there is no way to tell which users were exported — only that an impersonation session started at some point.

**Fix.** Add `await audit({ actorId: user.id, action: "account.export", entity: "User", entityId: user.id })` in the route (and mirror it in the admin CSV export at /api/admin/users/export). Tighten the rate limit from 5/min to something like 2/day per user, since legitimate portability exports are rare.

### The telegram deep-link provider is the only one that never checks account status — suspended users get a real JWT and an unexplained login loop

**MEDIUM** · `src/auth.ts:69` · confidence confirmed · effort S

**Claim.** `authorize` for the `telegram` provider goes `upsertTelegramUser(...)` → `if (!user) return null;` → return the principal. There is no `user.status !== "ACTIVE"` guard, unlike the `email-link` provider (auth.ts:91) and the `telegram-miniapp` provider (auth.ts:124) which both have one. A suspended user therefore receives a validly signed 7-day session cookie; `getCurrentUser` then resolves them to null on every request.

**Failure scenario.** A suspended user taps "Login with Telegram". The bot confirms, signIn returns success, the client redirects to `/${locale}` (telegram-deeplink-login.tsx:71). Every page renders logged-out, so any protected page bounces them straight back to /login, where they can loop forever with no error message and no mention of the suspension — while holding a real session cookie. Security-wise it is latent rather than live today (only /api/admin/impersonate reads raw `auth()`, and it re-checks role against the DB), but it means the signed session is no longer a reliable statement that the account is usable, so any future code that trusts `auth()` alone becomes an authz bypass.

**Fix.** Add `if (user.status !== "ACTIVE") return null;` after the transaction in auth.ts:69, matching the other two credentials providers, and surface a distinct `?error=suspended` on the login page so the user is told why.

### No session revocation: the 7-day JWT is a sliding window, and the code's "kills sessions" claims are false under the JWT strategy

**MEDIUM** · `src/auth.ts:21` · confidence confirmed · effort M

**Claim.** `session: { strategy: "jwt", maxAge: 7 * 24 * 60 * 60 }` with no `updateAge` override, so Auth.js re-issues the JWT on its default 24h rolling cadence — a cookie used at least once a week never expires. The `jwt` callback (auth.ts:167) carries only `token.uid`; there is no token version, jti, or not-before, and nothing anywhere consults a revocation list. `isDemotion` in src/lib/roles.ts:29 is documented "(→ revoke that user's sessions)" but `grep -rn isDemotion` across the repo returns only roles.ts and its own unit test — it is never called. `tx.session.deleteMany` at src/server/services/account.ts:214 ("Kill all access: sessions") and the admin UI copy at src/components/admin-user-manage.tsx:302 ("kills sessions") are both no-ops, because JWT sessions create no Session rows. docs/ENGINEERING-STANDARDS.md §4.1 — the yardstick — still describes an opaque 32-byte `fa_session` DB-backed cookie with a 30-day TTL and `consumeLoginNonce`, an architecture the code abandoned, so the authoritative contract promises revocation properties the implementation does not have.

**Failure scenario.** A creator's laptop is stolen or their session cookie is lifted from a shared machine. There is no "sign out other devices" control and no server-side handle on that session. Support's only lever is suspending the entire account (which does work — getCurrentUser re-reads status on every request), locking the legitimate owner out of their own orders and balance to evict the thief. Rotating AUTH_SECRET is the only alternative and logs out every user on the platform.

**Fix.** Add a `sessionEpoch Int @default(0)` to User; stamp it into the JWT in the `jwt` callback and compare it in `getCurrentUser`, bumping the column on password-less-device logout, admin suspension, and role demotion (wire up the already-written `isDemotion`). Set an explicit non-rolling absolute cap (`session.updateAge` plus an `iat`-based hard expiry) so a leaked cookie dies on a known date. Delete the dead `tx.session.deleteMany` line and the "kills sessions" UI copy, and rewrite ENGINEERING-STANDARDS.md §4.1 to describe the Auth.js JWT model that actually ships.

### A missing ADMIN_TELEGRAM_IDS silently and persistently demotes every admin, with no audit row

**MEDIUM** · `src/lib/session.ts:42` · confidence confirmed · effort S

**Claim.** The live reconciliation runs `resolveRole(user.telegramId, parseAdminIds(process.env.ADMIN_TELEGRAM_IDS))` and, on any mismatch, fire-and-forget writes the result: `void prisma.user.update({ ... data: { role: expected } }).catch(() => {})`. `parseAdminIds(undefined)` returns an empty Set (src/lib/roles.ts:10-15) and `resolveRole` then returns "BUYER" for everyone (roles.ts:20). There is no guard requiring the allowlist to be non-empty, and the role write emits no `audit()` entry — a silent privilege change, which contradicts docs/ENGINEERING-STANDARDS.md §12 "Audit every money/PII/admin action". The same unguarded path also *promotes*: any telegramId that appears in the env var becomes ADMIN on its owner's next page view, so the env var is a single unaudited string that grants platform-wide admin.

**Failure scenario.** A deploy ships without ADMIN_TELEGRAM_IDS in the container env (a new host, a rotated secrets file, a typo'd key). The first page view by each admin writes role=BUYER to their User row. /admin now redirects every admin to /dashboard (auth-guards.ts:57-63), gig moderation, KYC, disputes and payout approval are unreachable, and nothing in the audit log explains it — the AuditLog shows no role change at all, so the on-call engineer sees admins locked out with a clean trail. It self-heals once the env is restored, but only on the next request, and the outage window is invisible.

**Fix.** Refuse to reconcile against an empty allowlist: if `parseAdminIds(...)` is empty, skip the write entirely and log loudly (or fail boot via env.ts, since ADMIN_TELEGRAM_IDS is effectively a required secret). Await the update rather than firing it into the void, and emit `audit({ actorId: null, action: "user.role.reconcile", metadata: { from, to } })` on every transition so promotions and demotions both leave a trace.

## B — Authorization & IDOR (all ~76 routes under src/app/api/**)

### Seller self-approves any gig past moderation via action:"resume"

**HIGH → HIGH** (verified: CONFIRMED, reachable today) · `src/server/services/gig.ts:298` · confidence confirmed · effort S

**Claim.** `resumeGig` writes `status: "ACTIVE"` through `updateOwnedGig` (gig.ts:287-294), whose where-clause is `{...gigEditWhereForUser(gigId, user), deletedAt: null}` — correctly scoped to the OWNER, but with no precondition on the current status. Moving a gig to ACTIVE is otherwise an admin-only transition: `moderateGig` (gig.ts:335) throws FORBIDDEN for non-admins, and `publishGig` (gig.ts:413-419) deliberately routes an owner's DRAFT to PENDING_REVIEW, never ACTIVE. So the owner-scoped `resume` action is an unguarded back door around the admin gate. This isn't theoretical UI-only exposure: `GigRowActions` (src/components/gig-row-actions.tsx:42-46) renders the Resume button for EVERY status that isn't ACTIVE, so PENDING_REVIEW and REJECTED gigs get a working one-click Resume in the creator dashboard. The same root cause has a second lever: `updateGig` (gig.ts:196-256) replaces title, description, cover, gallery, FAQ, packages and extras wholesale and comments "Status is left unchanged", so an approved ACTIVE gig can be rewritten into arbitrary content without re-review. Gig moderation is currently one-time and reversible by the moderated party.

**Failure scenario.** A seller whose profile is APPROVED submits a benign gig; it lands PENDING_REVIEW (gig.ts:142). Instead of waiting, they open /dashboard/seller and click Resume on that row — or send `POST /api/gigs/<gigId>` with `{"action":"resume"}` and a same-origin Origin header. The gig flips to ACTIVE and, because the seller passes `PUBLIC_GIG_SELLER`, appears immediately on the marketplace, in search, and is orderable (`createOrder` only checks `status: "ACTIVE"`, order.ts:35). The identical request on a gig an admin explicitly REJECTED (with the rejection notice telling the seller to "fix and resubmit") republishes the rejected listing verbatim. Net effect: any approved creator can publish scam/policy-violating listings that no human ever approved, and can swap the content of an approved listing afterwards.

**Fix.** Give each transition its own precondition instead of sharing `updateOwnedGig`: `resumeGig` should scope to `status: "PAUSED"` (and throw CONFLICT otherwise), so only a gig the owner themselves paused can go back live. Route REJECTED/PENDING_REVIEW gigs through `publishGig`, and widen `publishGig`'s where-clause from `status: "DRAFT"` to `status: { in: ["DRAFT", "REJECTED"] }` so resubmission has a legitimate path that lands in PENDING_REVIEW. In `gig-row-actions.tsx`, render Resume only for `status === "PAUSED"` and a "Resubmit" for DRAFT/REJECTED. Separately, make `updateGig` demote an ACTIVE gig back to PENDING_REVIEW when moderated fields (title/description/cover/gallery/tags/FAQ) change, so approval survives edits.

> **Verification (CONFIRMED → HIGH).** Three things, two of which cut against the claimed blast radius and one that makes it worse. (a) Public visibility has a SECOND, independent gate the finding glosses: every public surface composes `PUBLIC_GIG_SELLER` (src/server/services/seller-visibility.ts:29-31 = `seller: { is: { isSeller: true, status: "ACTIVE", sellerProfile: { is: { approvalStatus: "APPROVED" } } } }`), and `approvalStatus: "APPROVED"` is written in exactly one place, `approveSeller` in admin-sellers.ts:85, behind `if (admin.role !== "ADMIN") throw Errors.forbidden` at line 70. So the attacker must already be a human-vetted seller — the exploit defeats PER-LISTING moderation, not the platform's first-contact moderation. (b) The finding notes `createOrder` (order.ts:34-35) only checks `status: "ACTIVE"` and omits PUBLIC_GIG_SELLER — true, but a buyer cannot reach an unapproved seller's gig page at all, because `getGigBySlug` (gig.ts:607-609) does compose PUBLIC_GIG_SELLER, so there is no discovery path to that gigId. (c) Worse than reported: the Resume button also fires on DRAFT (gig-row-actions.tsx:38-46 renders it for every status !== "ACTIVE"), so a DRAFT goes straight to ACTIVE, skipping PENDING_REVIEW entirely — sitting one pixel away from the correct `publish` button (line 33-37) that routes the same gig to PENDING_REVIEW. And the seller dashboard renders this for every gig regardless of status (dashboard/seller/page.tsx:361, fed by `listSellerGigs` whose where is only `{ sellerId, deletedAt: null }`, gig.ts:273). I could not find any middleware guard — src/middleware.ts:45 explicitly excludes `/api` from its matcher.

## E — Abuse &amp; Fraud Economics

### Reviews are gated on a COMPLETED order but not a REAL one — free unlimited 5★ farming, including into Google rich results

**CRITICAL → HIGH** (verified: CONFIRMED/DOWNGRADED, reachable today) · `src/server/services/review.ts:83` · confidence confirmed · effort S

**Claim.** `createReview` (review.ts:21-31) requires only `order.status === "COMPLETED"` and `order.buyerId === authorId`; it never checks `order.isTest`. `getGigReviews` (review.ts:83-99) aggregates every review for a gig with no `order: { isTest: false }` filter — unlike `recomputeSellerStats` (profile.ts:22-23) and `browse.ts:147`, which both filter it. **Failure scenario.** A seller with one already-approved gig registers a second account (any email; see the sybil finding). From the sybil: POST /api/orders {gigId,tier} → order auto-settles free. From the seller account: POST /api/orders/{id} {action:"deliver"}. From the sybil: {action:"accept"}, then POST /api/reviews {orderId,rating:5,comment:"..."}. **Fix.** Reject `order.isTest` in `createReview` (and `createBuyerReview`), and add `order: { isTest: false }` to all three queries in `getGigReviews` exactly as `recomputeSellerStats` already does. (2) The 'two numbers disagree on the same screen' bug exists RIGHT NOW with no attacker: with FREE_ORDERS=1 every one of the ~117 production orders is isTest, so gig pages render an unfiltered rating while profile.ts:22-23 renders 0. (3) The economic framing is off. 'Free' is a property of the temporary FREE_ORDERS flag, not of the review gate. The isTest gap is the amplifier; the missing per-(author, seller) dedupe is the actual hole. I downgrade CRITICAL→HIGH: this is marketplace-integrity fraud with no money loss, no auth bypass and no data exposure, on a pre-launch site with ~117 orders where the 'rich result' harm additionally requires Google to index and elect to render the stars.

> **Verification (DOWNGRADED → HIGH).** REACHABILITY BARRIER THE ORIGINAL GLOSSED OVER: this is approved-seller abuse, not an anonymous attack. Both the gig page and the order path require the attacker's own gig to be ACTIVE under an admin-APPROVED seller (getGigBySlug composes PUBLIC_GIG_SELLER, seller-visibility.ts:30; approvalStatus="APPROVED" is written in exactly one place, admin-sellers.ts:85, an admin-only action). ### Telegram webhook rate limit is keyed on Telegram's own IP — one abuser silently blackholes the bot for every user

**HIGH → MEDIUM** (verified: DOWNGRADED, reachable today) · `src/app/api/telegram/webhook/route.ts:35` · confidence confirmed · effort S

**Claim.** After the secret-header check, the webhook applies `rateLimit(\`tg-webhook:${clientIp(request)}\`, 120, 60_000)` and on exceed returns `NextResponse.json({ ok: true })` — a 200 (line 35-37). The client of a webhook is always Telegram's delivery server, so `clientIp` yields one of a handful of Telegram IPs for every user's traffic: this is a shared global bucket, not a per-abuser one. The per-user buckets (`tg-cb:${cbFrom}` at :80, `tg-reply:${from.id}` at :174) sit behind it and never get reached once the global bucket is exhausted. Cost: one Telegram account and a loop; payoff: the entire Telegram surface (auth, chat, order actions) is down for everyone, continuously, for as long as the loop runs.

**Fix.** Key the webhook bucket on the update's sender (`message.from.id` / `callback_query.from.id`) instead of the transport IP, keeping only a much higher global ceiling as a backstop. When the global backstop does trip, return a non-2xx so Telegram retries with backoff rather than dropping the update, and emit a warn log so the flood is visible.

> **Verification (DOWNGRADED → MEDIUM).** The mechanism is right; the HIGH rating overstates the consequence. (d) One point the finding got right and understated: the drop is not even logged — there is no `console.warn` on the exceed branch, so the outage is invisible in ops, which is arguably the worst property of the code as written.
